<TopicDefinition>

If someone asks what garbage collection is, I'd say it's the engine tidying up after you. JavaScript never asks you to free memory. Instead the collector watches which objects are still reachable — which ones something can still get to — and reclaims the rest.

The word to hold onto is reachable, not unused. An object you forgot about is still kept alive if a variable, a listener, or a cache can still reach it. That gap between "I stopped using it" and "nothing points at it" is where every memory leak lives.

Senior rounds usually go one step further: how the engine actually does it. Modern engines use mark-and-sweep — mark everything reachable from the roots, sweep away the rest — and V8 splits the heap into a young generation for objects that die fast and an old generation for the survivors.

</TopicDefinition>

<TopicTab value="examples">

<CodeExample title="Reachability decides what lives" language="javascript">
{`let user = { name: 'Sam' };
user = null;
// Setting user to null does not free the object.
// It only breaks one reference. The object is collected
// when NO path from a root reaches it — here, nothing else
// points at it, so the next pass can reclaim it.

function makeCycle() {
  const a = {};
  const b = {};
  a.other = b;
  b.other = a; // a and b point at each other
  return 'done';
}
makeCycle();
// A reference-counting collector would keep a and b forever:
// each one still has a reference. But nothing outside the
// function can reach them, so mark-and-sweep collects both.
console.log(makeCycle()); // 'done'`}</CodeExample>

<CodeExample title="The classic leak — and the fix" language="javascript">
{`// Node has a global EventTarget, just like a DOM node
const target = new EventTarget();
let hugeData = null;

function onResize() {
  console.log('rows:', hugeData.length);
}

function startDashboard() {
  hugeData = new Array(100_000).fill('row');
  target.addEventListener('resize', onResize);
}

function stopDashboard() {
  target.removeEventListener('resize', onResize);
  hugeData = null;
}

startDashboard();
// LEAK, if we stopped here: target still holds onResize,
// onResize closes over hugeData, so the array stays reachable
// long after startDashboard returns.

stopDashboard();
console.log(hugeData); // null — no path reaches the array, so it can be collected`}</CodeExample>

<CodeExample title="WeakRef: a cache that does not hold its values hostage" language="javascript">
{`const cache = new Map();

function getUser(id) {
  const cached = cache.get(id)?.deref();
  if (cached) return cached; // still alive — reuse it

  const user = { id, name: 'Sam' }; // pretend this is an expensive load
  cache.set(id, new WeakRef(user));
  return user;
}

const u1 = getUser('u1');
console.log(getUser('u1') === u1); // true — the cache hit while u1 is alive

// Once every strong reference to u1 is gone, the collector may
// reclaim it — and the next getUser('u1') quietly reloads instead
// of returning a stale object. The cache never keeps it alive.`}</CodeExample>

In the interview, say "reachable" instead of "unused". "The object is unreachable" is the senior answer. "I stopped using it" is the junior one — the collector cannot tell what you stopped using, only what nothing points at.
</Callout>

<TopicTab value="indepth">

### Reachability is the only question

The collector never asks whether you still need an object. It asks whether a path exists from a root — a global variable, a local on the current call stack, or a live DOM node — through references to that object. If a path exists, the object lives. If not, it is garbage. A leak is therefore never "memory the engine forgot to free". It is a path you forgot to break.

### Mark-and-sweep in two passes

The mark pass starts at the roots and walks every reference, marking each object it reaches as alive. The sweep pass reclaims everything unmarked. Circular references are collected because reachability, not counting, decides the outcome — two objects pointing at each other are still swept away if nothing outside them points in. That is the exact case the old reference-counting collectors leaked on.

### V8's generational shortcut

Most objects die young, so V8 splits the heap in two. New objects land in the young generation, which is small and collected often and cheaply. Objects that survive a few collections get promoted to the old generation, which is collected rarely with a full mark-sweep-compact pass. The practical upshot: short-lived throwaway objects are nearly free, and long-lived caches and globals are the ones that cost you.

### WeakRef and FinalizationRegistry

A `WeakRef` holds a reference that does not keep its object alive. `deref()` returns the object while it is still in memory and `undefined` once it has been collected — the right shape for a cache of expensive objects you are happy to rebuild. `FinalizationRegistry` goes one step further: you register an object with a cleanup callback that runs after it is reclaimed, which is how you release outside resources like file handles. Both are non-deterministic — the callback may run late or never — so neither one belongs in essential program logic. One more caveat: a `Map` of `WeakRef` values still accumulates stale keys, and `FinalizationRegistry` is how you prune them.

### Senior follow-ups

Be ready to name four leak patterns — accidental global, forgotten timer, unremoved listener, detached DOM node or unbounded cache — and to describe finding one: take heap snapshots in DevTools before and after the suspect action, compare retained objects, and follow the retaining path back to the root. In Node, `--inspect` gives you the same heap tools.
