<TopicDefinition>

If someone asks the difference between `==` and `===`, I'd say: `===` compares type and value with no conversion — different types, immediately false. `==` tries to convert the operands to a common type first, then compares.

Interviewers don't really want the textbook line. They want the rule set: same type behaves like `===`; `null` and `undefined` are a special pair; a string compared to a number converts the string to a number; a boolean converts to a number first; an object compared to a primitive goes through `valueOf`/`toString`. Every "weird" result — `[] == false`, `'' == 0` — falls straight out of these.

Senior rounds always ask the same follow-up: is `==` ever okay? Yes, exactly once — `x == null` catches `null` or `undefined` in one check, and it's false for `0` and `''`. Everything else, `===`.

</TopicDefinition>

<CodeExample title="The == rule set in six lines" language="javascript">
{`5 === '5';            // false — different types, no conversion
5 == '5';             // true — string converts to number

true == 1;            // true — boolean converts to number first
false == '';          // true — false → 0, '' → 0

null == undefined;    // true — the special pair, no coercion
null == 0;            // false — null equals ONLY undefined
NaN == NaN;           // false — NaN equals nothing, not even itself`}
</CodeExample>

<CodeExample title="Walking through [] == false" language="javascript">
{`// [] == false — say each step out loud in an interview:
// 1. [] is an object vs a primitive → convert: [].toString() is ''
// 2. '' == false — boolean converts to a number first: false → 0
// 3. '' == 0 — string converts to a number: '' → 0
// 4. 0 === 0 → true
console.log([] == false);  // true

// Same machinery, different trap:
console.log([] == ![]);    // true — ![] is false, then the same walk`}
</CodeExample>

<CodeExample title="Object.is vs === — the two differences" language="javascript">
{`0 === -0;               // true — same numeric value
Object.is(0, -0);       // false — Object.is distinguishes the signs

NaN === NaN;            // false — NaN is never equal to itself
Object.is(NaN, NaN);     // true

// React compares state and props with Object.is:
// setState(NaN) when state was already NaN bails out — no infinite re-render`}
</CodeExample>

<Callout type="interview">
When `==` mixes types in an interview, narrate the conversion order out loud: **"object to primitive, then boolean to number, then string to number."** Saying the order beats reciting the answer.
</Callout>

<TopicTab value="indepth">

### The three comparisons

- `==` — **abstract equality**. Symmetric, deterministic, small rule set. Same type falls back to `===`.
- `===` — **strict equality**. Type and value, no conversion. The default for everything.
- `Object.is` — **sameness**. Identical to `===` except `NaN` equals itself and `+0` ≠ `-0`.

### Senior follow-ups

Be ready to defend exactly one `==`: `x == null`. It's the null-or-undefined guard that predates `??`, still idiomatic in many codebases, and — critically — it stays false for `0` and `''`, which is what separates it from a sloppy truthiness check.

Know why `Object.is` exists beyond trivia: it's what React uses under the hood for the bail-out check in `useState` and `React.memo`. That means a senior candidate can explain *why* `Object.is(NaN, NaN)` matters — without it, a state update to `NaN` would never converge.

And the trap interviewers reach for when you say "always `===`": "So how do you check for `NaN`?" Answer: never with equality — `Number.isNaN(x)`, because `x !== x` works but reads like a riddle.

</TopicTab>
