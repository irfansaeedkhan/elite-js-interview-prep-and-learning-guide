<TopicDefinition>

If someone asks what a callback is, I'd say: it's a function you hand to another function, to be called **later**. "Call me back when you're done." Timers, network requests, event listeners — they all take callbacks.

The trap interviewers probe is assuming every callback is async. It's not — the callback doesn't decide. The caller does. `forEach` runs your callback right away; `setTimeout` parks it until the timer fires.

Senior rounds go one layer deeper: **error handling** (the error-first `(err, result)` convention) and **trust** (once your callback is inside someone else's code, they can call it never, twice, or synchronously). That's the real reason promises exist.

</TopicDefinition>

<CodeExample title="Sync vs async callbacks" language="javascript">
{`// The callback doesn't decide when it runs — the caller does.
console.log('A');

[1, 2].forEach((n) => console.log('sync', n)); // runs right now

setTimeout(() => console.log('async'), 0);     // runs after A..Z

console.log('Z');
// A, sync 1, sync 2, Z, async`}
</CodeExample>

<CodeExample title="Error-first convention (Node.js style)" language="javascript">
{`function readFileFake(path, callback) {
  setTimeout(() => {
    if (!path) {
      callback(new Error('no path given'), null); // error first
      return;                                     // always return after err
    }
    callback(null, 'file contents');              // null error = success
  }, 100);
}

readFileFake('/a.txt', (err, data) => {
  if (err) {
    console.error('failed:', err.message);
    return; // handle it or bail — never fall through
  }
  console.log('got:', data);
});`}
</CodeExample>

<CodeExample title="Callback hell, then flattened" language="javascript">
{`// Callback hell: each step nests inside the previous one.
getUser(id, (user) => {
  getOrders(user.id, (orders) => {
    getTotals(orders, (total) => {
      console.log(total); // pyramid of doom
    });
  });
});

// Same flow with named functions — flat and readable.
function onUser(user)    { getOrders(user.id, onOrders); }
function onOrders(orders) { getTotals(orders, onTotal); }
function onTotal(total)   { console.log(total); }
getUser(id, onUser);`}
</CodeExample>

<TopicTab value="indepth">

### The traps interviewers actually set

**1. "Never release Zalgo"** — an API that calls your callback synchronously *sometimes* and asynchronously *other times* creates ordering bugs that only appear in production. Promises fix this: `.then` callbacks are always async, even for already-resolved values.

**2. Called twice (or never).** Nothing stops a buggy library from invoking your callback twice — charging a customer twice, appending two DOM nodes. The `callOnce` challenge below is the real-world guard.

**3. Errors get swallowed.** Inside nested callbacks, a thrown error doesn't bubble to your try/catch — it lands in the event loop and vanishes. That's why error-first callbacks check `err` first, and why promise chains use `.catch`.

### Worked example: bridging callbacks to promises

This is the interview classic — wrap any error-first function so it returns a promise:

{`function promisify(fn) {
  return (...args) =>
    new Promise((resolve, reject) => {
      fn(...args, (err, result) => {
        if (err) reject(err);
        else resolve(result);
      });
    });
}

// Usage: const readFile = promisify(readFileFake);
// readFile('/a.txt').then(console.log).catch(console.error);`}

Node ships this as `util.promisify` — but interviewers often ask you to write it by hand.
