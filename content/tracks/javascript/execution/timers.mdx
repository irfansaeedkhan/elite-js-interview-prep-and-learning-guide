<TopicDefinition>

If someone asks about timers, I'd say: `setTimeout` runs a function once, later. `setInterval` runs it again and again until you stop it. That's the whole API — the interview lives in the word "later".

Later does not mean "after exactly this many milliseconds". It means "no earlier than this, and only once the current code has finished". A timer callback is a macrotask: it waits in line behind everything already running, and behind microtasks like promise callbacks.

That one fact explains the three traps interviewers love: `setTimeout(fn, 0)` still runs last, a busy loop delays every timer, and a `var` loop prints the same number five times. Get the mental model right and the traps answer themselves.

</TopicDefinition>

<TopicTab value="examples">

<CodeExample title="setTimeout(fn, 0) still runs last" language="javascript">
{`// Zero delay means "as soon as possible", not "right now".
console.log('first');

setTimeout(() => console.log('timer'), 0);

Promise.resolve().then(() => console.log('promise'));

console.log('last');
// first, last, promise, timer
// The timer waits for the stack to empty AND for microtasks.`}
</CodeExample>

<CodeExample title="The classic loop trap, and the fix" language="javascript">
{`// TRAP: var makes ONE shared i. Every callback reads it after the loop ends.
for (var i = 1; i <= 3; i++) {
  setTimeout(() => console.log(i), i * 100);
}
// 4, 4, 4 — the loop finished before any callback ran.

// FIX 1: let gives each iteration its own i.
for (let j = 1; j <= 3; j++) {
  setTimeout(() => console.log(j), j * 100);
}
// 1, 2, 3

// FIX 2 (if the interviewer insists on var): capture the value per iteration.
for (var k = 1; k <= 3; k++) {
  (function (value) {
    setTimeout(() => console.log(value), value * 100);
  })(k);
}
// 1, 2, 3 — the IIFE hands each callback its own copy.`}
</CodeExample>

<CodeExample title="Cancelling timers and passing arguments" language="javascript">
{`// setTimeout returns an id — keep it if you might need to cancel.
const id = setTimeout(() => console.log('never prints'), 1000);
clearTimeout(id); // changed your mind before it fires

// setInterval needs clearInterval, or it runs forever.
const intervalId = setInterval(() => console.log('tick'), 1000);
setTimeout(() => clearInterval(intervalId), 3500); // ticks ~3 times, then stops

// Extra arguments after the delay are passed straight to the callback.
setTimeout((name) => console.log('hello', name), 500, 'Irfan');
// No wrapper arrow function needed just to pass a value.`}
</CodeExample>

<TopicTab value="indepth">

### The traps interviewers actually set

**1. Delay is a minimum, not a promise.** The timer thread counts down on its own, but the callback can only run when the call stack is empty. A 100ms timer set right before a 2-second blocking loop fires after the loop, not at 100ms. Never build a clock or countdown on raw timer counts alone — compare `Date.now()` against a target time if accuracy matters.

**2. setInterval does not wait.** It schedules from the start of each run, so if a callback takes longer than the interval, the next run fires immediately after it finishes — or several queue up. For anything that can be slow (network polling, heavy DOM work), prefer recursive `setTimeout`: schedule the next run when the current one ends, so the gap is real.

**3. Nested timers get clamped.** Browsers enforce a minimum 4ms delay once timers nest more than five levels deep. A tight recursive loop therefore never runs faster than 4ms per step in a browser, even with a delay of 0. Node has `setImmediate` for the "run right after this" case; browsers do not.

**4. Forgotten intervals leak.** An interval keeps running until `clearInterval` — across route changes, after a component unmounts, after the user gave up waiting. In React, always clear timers in the cleanup function. In plain code, pair every `setInterval` with the code path that stops it.

### Worked example: polling with backoff

This is the pattern interviewers accept as the "better than setInterval" answer — poll, wait for the result, then decide the next delay:

{`function poll(fetchStatus, { delay = 1000, maxDelay = 30000 } = {}) {
  let timerId = null;
  let stopped = false;

  function tick() {
    if (stopped) return;
    fetchStatus()
      .then((done) => {
        if (done || stopped) return;
        // Still pending, server healthy: poll again at the same pace.
        timerId = setTimeout(tick, delay);
      })
      .catch(() => {
        // Server failed: back off instead of hammering it.
        if (stopped) return;
        delay = Math.min(delay * 2, maxDelay);
        timerId = setTimeout(tick, delay);
      });
  }

  timerId = setTimeout(tick, delay);
  // Caller stops it like this: stop();
  return function stop() {
    stopped = true;
    clearTimeout(timerId);
  };
}

// Usage: const stop = poll(checkOrderStatus);
// Later: stop(); — no stray timer keeps polling after you leave.`}

Note what this buys over `setInterval`: the gap is measured from the end of each request, the delay adapts to failures, and there is exactly one scheduled callback at a time — no overlap, no pile-up.
