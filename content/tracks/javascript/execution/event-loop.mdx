<TopicDefinition>

JavaScript runs on a **single thread** with one **call stack**. It cannot run two functions at the same time in that thread. Yet we use timers, network requests, and Promises without blocking the UI.

The **event loop** is the coordinator: when the stack is empty, it pulls work from queues and pushes callbacks back onto the stack. Understanding this model is non-negotiable for senior JavaScript interviews — especially output-prediction questions.

</TopicDefinition>

### Mental model — call stack first

Before async enters the picture, synchronous code runs top to bottom on the call stack:

<MermaidDiagram caption="Synchronous execution — one frame at a time" size="inline">
{`flowchart TB
    subgraph stack["Call Stack"]
        A["main()"]
        B["console.log start"]
        C["calculate()"]
    end
    A --> B --> C
`}
</MermaidDiagram>

Each function pushed onto the stack must **finish and pop** before the next queued work runs.

<CodeExample title="Stack builds and drains" language="javascript">
{`function calculate() {
  return 2 + 2;
}

console.log('start');
const result = calculate();
console.log(result);
console.log('end');`}
</CodeExample>

### Output prediction — classic interview pattern

<CodeExample title="Predict the output" language="javascript" runnable>
{`console.log('A');

setTimeout(() => console.log('B'), 0);

Promise.resolve().then(() => console.log('C'));

console.log('D');

// Your prediction: A, D, C, B`}
</CodeExample>

<Callout type="interview">
Say your answer **out loud with reasoning**: "Sync A and D first, then microtask C, then macrotask B."
</Callout>

</TopicTab>

<TopicTab value="indepth">

When you call `setTimeout` or `fetch`, the browser handles the timer or network. When ready, the callback waits in a **task queue**. The event loop's job: *if stack is empty, dequeue and run*.

### Microtasks vs macrotasks

**Microtasks** (Promises, `queueMicrotask`) drain completely after each stack turn, **before** the next **macrotask** (`setTimeout`, I/O, rendering).

<Figure
  src="/diagrams/javascript/event-loop-browser.svg"
  alt="Browser event loop architecture"
  caption="Browser model (Excalidraw → SVG). Web APIs hold timers and network; queues feed the stack when empty."
  size="section"
/>

<Callout type="gotcha">
`setTimeout(fn, 0)` does **not** mean "run immediately." It means "schedule a macrotask after current sync code and **all** pending microtasks."
</Callout>

<MermaidDiagram caption="One event loop tick — microtasks drain first" size="section">
{`sequenceDiagram
    participant Stack as Call Stack
    participant Micro as Microtask Queue
    participant Macro as Macrotask Queue
    participant EL as Event Loop

    Stack->>Stack: Run sync code
    Stack->>Micro: Drain ALL microtasks
    Micro->>Stack: Promise.then and queueMicrotask
    EL->>Macro: Take next macrotask
    Macro->>Stack: setTimeout or IO callback
`}
</MermaidDiagram>

### Node.js — not identical to the browser

In Node, **libuv** drives the loop with phases. `process.nextTick` runs even before Promise microtasks.

<MermaidDiagram caption="Node.js libuv phases (simplified)" size="full">
{`flowchart LR
    subgraph node["Node Event Loop"]
        T[Timers]
        P[Pending callbacks]
        I["idle and prepare"]
        Po[Poll]
        Ch[Check]
        Cl[Close callbacks]
    end
    T --> P --> I --> Po --> Ch --> Cl --> T
`}
</MermaidDiagram>

<Callout type="tip">
For **browser** interviews, focus on stack + microtask + macrotask. For **Node**, add `process.nextTick` and libuv phases.
</Callout>

Because microtasks drain **completely** before the next macrotask. A recursive `Promise.then` chain keeps the stack busy with microtasks and delays rendering, timers, and user input handling.
