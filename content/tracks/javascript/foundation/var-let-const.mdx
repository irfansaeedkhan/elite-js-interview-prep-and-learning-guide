<TopicDefinition>

If someone asks the difference between `var`, `let`, and `const`, I'd say `var` is the old one — it ignores blocks and leaks to the whole function, and it's initialized to `undefined` even before its line runs. `let` and `const` are block-scoped and were added to fix exactly that.

The trap interviewers love is the **temporal dead zone**: `let` and `const` are hoisted too, but reading them before the declaration line throws a ReferenceError. "It's hoisted, just uninitialized" is the senior version of the answer.

Senior rounds also probe the **loop trap** — `for (var i ...)` with async callbacks sees the final value every time, because closures capture the variable, not a copy of its value. Swapping to `let` gives each iteration its own binding. That's the one to have rehearsed.

</TopicDefinition>

{`function scopeDemo() {
  if (true) {
    var leaked = 'var ignores blocks';
    let kept = 'let stays in the block';
  }
  console.log(leaked); // 'var ignores blocks'
  console.log(kept);   // ReferenceError: kept is not defined
}

console.log(hoisted);  // undefined — var is hoisted AND initialized
var hoisted = 1;`}
</CodeExample>

<CodeExample title="The temporal dead zone" language="javascript">
{`{
  console.log(a); // ReferenceError: Cannot access 'a' before initialization
  let a = 1;      // the TDZ ends here

  console.log(b); // undefined — no TDZ for var
  var b = 2;
}`}
</CodeExample>

<CodeExample title="const locks the binding, not the contents" language="javascript">
{`const user = { name: 'Ada' };
user.name = 'Grace';      // fine — mutating contents
user = { name: 'Lin' };   // TypeError: Assignment to constant variable

const tags = ['js'];
tags.push('ts');          // fine
// tags = [];             // TypeError`}
</CodeExample>

Say **"the binding, not the value"** for const, and **"hoisted but uninitialized"** for the TDZ. Those phrases land.

<TopicTab value="indepth">

<CodeExample title="The famous loop trap, walked through" language="javascript">
{`// prints 3, 3, 3 — one shared 'i' across all iterations
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}

// prints 0, 1, 2 — 'let' gives every iteration a fresh binding
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log(j), 0);
}

// the pre-ES6 fix: a function call per iteration captures the value
for (var k = 0; k < 3; k++) {
  (function (value) {
    setTimeout(() => console.log(value), 0);
  })(k);
}`}
</CodeExample>

<CodeExample title="Redeclaration and the for-of habit" language="javascript">
{`var x = 1;
var x = 2; // allowed — silently overwrites, another reason to avoid var

// let x = 3; // SyntaxError: Identifier 'x' has already been declared

for (const item of ['a', 'b']) {
  // const works in for-of: each iteration re-declares it
  console.log(item);
}`}
</CodeExample>

### Senior follow-ups

- **Is let hoisted?** Yes — the engine knows the name exists, which is exactly why touching it early throws a ReferenceError instead of returning `undefined`.
- **Why avoid var in new code?** Function scoping leaks across blocks, redeclaration is silently allowed, and the hoisted `undefined` masks bugs the TDZ would surface.
- **When do you use let over const?** Only when the variable is genuinely reassigned — counters, accumulators, swap variables. Default to const and let the compiler catch accidents.
