<TopicDefinition>

If someone asks me what scope is, I'd say it's the answer to "which variables can this code see?" And the word that matters most is **lexical**: that answer is decided by where the code is **written**, not where it runs. A function looks up variables in the scopes wrapped around its definition — even if you call it from the other side of the codebase.

Interviewers care about this because the `var` vs `let` difference lives here. `var` is function-scoped, so a loop shares one binding across every iteration — that's the classic "all my handlers log the same number" bug. `let` and `const` are block-scoped, and `let` in a loop creates a fresh binding per iteration, which is why switching one keyword fixes it.

Senior rounds push one step further, into the **temporal dead zone**: `let` and `const` are hoisted but unusable before their declaration line, so reading early throws instead of silently giving `undefined`. And they ask what closures cost — a function that escapes keeps its whole defining scope alive, which is powerful for private state and a real way to leak memory.

</TopicDefinition>

<TopicTab value="examples">

<CodeExample title="Lexical lookup — definition site wins" language="javascript">
{`const name = 'outer';

function greet() {
  return name; // looks up the scope where greet was WRITTEN
}

function run() {
  const name = 'caller';
  return greet(); // still 'outer' — the caller's scope is irrelevant
}

console.log(run()); // 'outer'

// And the reverse fails: an outer scope cannot see inside
function make() {
  const secret = 'hidden';
}
console.log(typeof secret); // 'undefined' — secret never leaves make`}
</CodeExample>

<CodeExample title="The var loop trap, and the let fix" language="javascript">
{`// var: ONE binding shared by every iteration
const varHandlers = [];
for (var i = 0; i < 3; i++) {
  varHandlers.push(() => i);
}
console.log(varHandlers.map((f) => f())); // [3, 3, 3] — loop finished first

// let: a FRESH binding per iteration
const letHandlers = [];
for (let j = 0; j < 3; j++) {
  letHandlers.push(() => j);
}
console.log(letHandlers.map((f) => f())); // [0, 1, 2]

// The old-school fix for var: give each iteration its own scope
const fixedHandlers = [];
for (var k = 0; k < 3; k++) {
  fixedHandlers.push(((n) => () => n)(k));
}
console.log(fixedHandlers.map((f) => f())); // [0, 1, 2]`}
</CodeExample>

<CodeExample title="TDZ and shadowing in one block" language="javascript">
{`// TDZ: the binding exists but you cannot touch it yet
function demo() {
  // console.log(value); // ReferenceError — TDZ, not undefined
  let value = 'ready';
  return value;
}

// var behaves differently — hoisted AND initialized to undefined
function oldDemo() {
  console.log(old); // undefined, no error
  var old = 'late';
}

// Shadowing: the inner name wins inside its block, outer untouched
const role = 'admin';
if (true) {
  const role = 'guest'; // a different binding, not an overwrite
  console.log(role);    // 'guest'
}
console.log(role);      // 'admin'`}
</CodeExample>

<TopicTab value="indepth">

### What to focus on

- The mental model: scope is a chain of environments, searched outward from where code is written
- The three declarations: `var` (function scope, initialized `undefined`), `let`/`const` (block scope, TDZ until declaration)
- The loop trap: one shared `var` binding vs a fresh `let` binding per iteration
- Closures: a function carries its defining scope with it, with live references, not copies

### Senior follow-ups

Be ready to explain why `let` in a `for` header is special — the spec effectively creates a new declarative environment per iteration, which is the mechanism behind the fix, not just a happy accident. Know the `typeof` asymmetry: `typeof` on a truly undeclared variable is `'undefined'`, but `typeof` on a TDZ variable still throws, because the binding exists and is uninitialized. And be honest about the cost of closures: captured variables stay alive as long as the function does, so a long-lived handler closing over a huge object is a memory leak with a respectable name — the fix is to capture only what you need, or null out the reference when done.

</TopicTab>
