<TopicDefinition>

If someone asks me what a closure is, I'd say it's a function that **remembers where it was written**. When an inner function uses a variable from its outer function, that variable stays alive for the inner function — even after the outer function has finished and returned.

Interviewers care because this is where real code lives. Every callback, timer, and event handler is a function running long after its creator finished. And it's where the classic trap lives: a loop that shares one variable across all its callbacks.

The senior nuance is that a closure holds the **binding, not a snapshot**. Change the variable later and the closure sees the new value. That one fact explains both the loop trap and why two counters from the same factory never share state.

</TopicDefinition>

<TopicTab value="examples">

<CodeExample title="Private counter" language="javascript">
{`function createCounter() {
  let count = 0;
  return {
    increment() { count += 1; return count; },
    getCount() { return count; },
  };
}

const counter = createCounter();
counter.increment();
console.log(counter.getCount()); // 1`}
</CodeExample>

<CodeExample title="Loop trap with let" language="javascript">
{`for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 0, 1, 2 — each iteration gets its own i binding`}
</CodeExample>

<CodeExample title="A closure sees later changes" language="javascript">
{`let message = 'first';
function readMessage() {
  return message;
}

message = 'second';
console.log(readMessage()); // 'second' — the binding, not a snapshot`}
</CodeExample>

<CodeExample title="Two counters, separate state" language="javascript">
{`const first = createCounter();
const second = createCounter();

first.increment();
first.increment();
console.log(first.getCount()); // 2
console.log(second.getCount()); // 0 — a fresh count per call`}
</CodeExample>

<TopicTab value="indepth">

Walk through the `var` loop out loud, step by step. `var` is function-scoped, so the loop has **one** `i` binding, shared by all three timer callbacks. The loop runs to completion first — `i` ends at 3 — and only then do the timers fire. Each callback reads the same binding, so you get 3, 3, 3. With `let`, each iteration gets its **own** binding, so the callbacks read 0, 1, 2.

<Callout type="interview">
Say the mechanism, not just the fix: "One shared binding, read after the loop finished." Then name the fix: `let`, an IIFE taking `i` as a parameter, or `forEach` with its own callback parameter.
</Callout>

<Callout type="gotcha">
A closure keeps everything it references alive. A long-lived handler closing over a big object or a DOM node holds that memory until the handler itself goes away — remove listeners you no longer need.
</Callout>

</TopicTab>
