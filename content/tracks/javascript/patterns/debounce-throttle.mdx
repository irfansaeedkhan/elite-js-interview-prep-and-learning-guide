<TopicDefinition>

If someone asks what debounce and throttle are, I'd say they're both answers to the same problem: some events fire far more often than you can afford to handle — every keystroke, every scroll pixel. Debounce waits for a pause and then runs once. Throttle runs at most once per interval while the noise continues.

What interviewers actually test is whether you can write one from scratch, because the whole implementation is three ideas: a **closure** holding the timer id, `clearTimeout` to cancel the pending call, and `setTimeout` to schedule the next one. Debounce clears and reschedules on every call, so only the last call in a burst survives. Throttle runs the first call and ignores everything until the interval passes.

Senior rounds go after the edges: is your throttle leading, trailing, or both — and does it silently drop the last call of a burst? And in React: why does recreating the debounced function on every render mean the delay never completes? Those two questions separate "read the docs" from "debugged this in production."

</TopicDefinition>

<TopicTab value="examples">

<CodeExample title="Debounce from scratch" language="javascript">
{`function debounce(fn, wait) {
  let timer = null;                       // lives in the closure — one timer per debounced fn
  function debounced(...args) {
    clearTimeout(timer);                  // cancel the pending call...
    timer = setTimeout(() => fn.apply(this, args), wait); // ...schedule a fresh one
  }
  debounced.cancel = () => clearTimeout(timer);
  return debounced;
}

const search = debounce((query) => fetchResults(query), 300);
// user types "r", "re", "rea", "reac", "react" fast:
// only "react" is sent, 300ms after the last keystroke`}
</CodeExample>

<CodeExample title="Throttle from scratch (leading + trailing)" language="javascript">
{`function throttle(fn, wait) {
  let last = 0;
  let timer = null;
  let lastArgs = null;

  return function (...args) {
    const now = Date.now();
    const remaining = wait - (now - last);
    lastArgs = args;                      // always keep the freshest arguments

    if (remaining <= 0) {
      last = now;
      fn.apply(this, args);               // leading edge — run now
    } else if (timer === null) {
      timer = setTimeout(() => {          // trailing edge — run the latest once
        timer = null;
        last = Date.now();
        fn.apply(this, lastArgs);
      }, remaining);
    }
  };
}

const track = throttle((pos) => sendAnalytics(pos), 1000);
// scrolls continuously for 5s: fires at t=0, then every 1s,
// plus one final call with the last position — nothing lost`}
</CodeExample>

<CodeExample title="Leading-edge debounce for instant actions" language="javascript">
{`function debounce(fn, wait, { leading = false } = {}) {
  let timer = null;
  return function (...args) {
    const callNow = leading && timer === null;
    clearTimeout(timer);
    timer = setTimeout(() => {
      timer = null;
      if (!leading) fn.apply(this, args);
    }, wait);
    if (callNow) fn.apply(this, args);    // first call of the burst runs now
  };
}

// submit button: act instantly, swallow double-clicks
form.addEventListener('submit', debounce(handleSubmit, 500, { leading: true }));
// "a" submits, "b"/"c" within 500ms are ignored,
// a submit after the quiet period works again`}
</CodeExample>

<TopicTab value="indepth">

<Callout type="gotcha">
The naive throttle **drops the trailing call**. The flag version — run once, set `inThrottle = true`, reset it after the interval — fires the first call of a burst and silently discards the rest. That means the *final* scroll position or the *final* form state never gets processed. If the last value matters, you need a trailing edge: stash the latest arguments and flush them when the cooldown ends (like the implementation in the examples tab).
</Callout>

<Callout type="tip">
In React, **create the debounced function once**. A new `debounce(fn, 300)` on every render resets the closure's timer state, so the delay never completes and every keystroke fires. Wrap it in `useMemo` (or store it in a ref), and call `.cancel()` in the effect cleanup so a pending call can't fire after unmount.
</Callout>

<Callout type="tip">
Debounce and throttle control *how often* a function runs — they never make a slow function fast. If a click handler janks, profile the handler; don't debounce the click. And never stack both on the same event source — pick one strategy per event and be deliberate about the delay (300ms feels instant on search; past ~500ms starts feeling sluggish).
</Callout>

<CodeExample title="Which one for which job" language="javascript">
{`// ONLY the finished value matters → debounce
input.addEventListener('input', debounce((e) => searchAPI(e.target.value), 300));
// autosave after the user pauses
editor.addEventListener('input', debounce(saveDraft, 1000));

// UPDATES NEEDED DURING the action → throttle
window.addEventListener('scroll', throttle(updateProgressBar, 100));
// steady analytics flow, not one event per pixel
window.addEventListener('mousemove', throttle(sendHeartbeat, 2000));

// MUST FEEL INSTANT, EVERY TIME → neither
button.addEventListener('click', addToCart); // don't debounce this`}
</CodeExample>
