<TopicDefinition>

If someone asks what memoization is, I'd say it's remembering a function's answers. You call an expensive function once with some inputs, store the result, and the next time the same inputs show up you return the stored answer instead of recomputing.

Interviewers almost always follow up with the **cache key**, because that's where memoization actually lives or dies. One primitive argument is easy — the argument is the key. Several arguments need something that keeps `(1, 2)` and `(2, 1)` apart, and objects key by **reference**, not contents: two objects that look equal are different keys.

In senior rounds you hear about the price. The cache only grows, so memoizing over user IDs in a long-lived server is a slow memory leak. Real implementations cap the cache, expire entries, or use a `WeakMap` for object keys — and they only memoize functions that are pure and actually expensive.

</TopicDefinition>

<TopicTab value="examples">

<CodeExample title="The basic memoize, and why it pays off" language="javascript">
{`function memoize(fn) {
  const cache = new Map();
  return function (...args) {
    const key = args[0];
    if (cache.has(key)) return cache.get(key);
    const result = fn(...args);
    cache.set(key, result);
    return result;
  };
}

let calls = 0;
const fib = memoize((n) => {
  calls++;
  return n < 2 ? n : fib(n - 1) + fib(n - 2);
});

console.log(fib(10)); // 55
console.log(calls);   // 11 — not 177. Each n computed once.`}</CodeExample>

<CodeExample title="The falsy-result trap" language="javascript">
{`// WRONG: truthiness check treats cached falsy results as misses
function broken(fn) {
  const cache = new Map();
  return (x) => cache.get(x) || fn(x); // 0, '', false never stick
}

// RIGHT: Map.has asks "is there an entry?", not "is it truthy?"
function fixed(fn) {
  const cache = new Map();
  return (x) => {
    if (cache.has(x)) return cache.get(x);
    const result = fn(x);
    cache.set(x, result);
    return result;
  };
}

let calls = 0;
const zero = fixed(() => { calls++; return 0; });
zero(); zero();
console.log(calls); // 1 — the cached 0 counts as a hit`}</CodeExample>

<CodeExample title="The key-collision trap" language="javascript">
{`// WRONG: joining arguments collides — ['a', 'b'] and ['a,b'] agree
const key = (args) => args.join(',');
console.log(key(['a', 'b'])); // 'a,b'
console.log(key(['a,b']));    // 'a,b' — same key, different call

// RIGHT: nested Maps keep every argument separate, no string tricks
function memoizeMulti(fn) {
  const root = new Map();
  return function (...args) {
    let node = root;
    for (const arg of args) {
      if (!node.has(arg)) node.set(arg, new Map());
      node = node.get(arg);
    }
    if (node.has('result')) return node.get('result');
    const result = fn(...args);
    node.set('result', result);
    return result;
  };
}

const add = memoizeMulti((a, b) => a + b);
console.log(add(1, 2)); // 3, computed
console.log(add(2, 1)); // 3, computed separately — no collision`}</CodeExample>

<TopicTab value="indepth">

### When not to memoize

Memoization is only sound for **pure** functions: same inputs, same output, no side effects. Memoize something that reads `Date.now()`, randomness, or outside state and you cache a stale answer. And don't memoize cheap functions — building a key plus a `Map` lookup can cost more than the function itself. Measure first.

### Bounding the cache

One entry per distinct key, forever, is a leak. Three fixes, pick by key type:

- **Object keys → `WeakMap`.** Entries disappear when the key object is garbage collected, so the cache can't outlive its keys by construction.
- **Primitive keys → size cap.** `Map` keeps insertion order, so evicting `cache.keys().next().value` drops the oldest entry in one line; delete and re-set on every hit if you want true least-recently-used order.
- **Async results → TTL.** Cache the promise immediately (so concurrent callers share one request), delete failed entries so retries work, and expire entries after a timeout.

### The React connection

`useMemo` is this same idea scoped to one component: cache a value, recompute only when dependencies change. Dependencies compare by reference, so an object literal rebuilt every render defeats it — the same reference-vs-value trap as the cache key. And like any memoization, it's a targeted optimization after profiling, not a default wrapper.

<Callout type="gotcha">
Every cache hit returns the **same object reference**. If one caller mutates the returned object, every later caller sees the mutation. Memoize values you treat as read-only, or return copies.
</Callout>
