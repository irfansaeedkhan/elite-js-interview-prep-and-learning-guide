<TopicDefinition>

If someone asks me to design a chat app, I would say it is a message list where sending feels instant, order is guaranteed by the server, and reconnects lose nothing. The chat window looks like the simplest UI in the world. The hard parts are all invisible: optimistic updates, ordering, delivery states, and resume.

Interviewers care because chat punishes every async shortcut. No cancellation story, no ordering story, and no reconnect story all show up as duplicated messages, lost messages, or a list that jumps while you read it.

The senior nuance is honesty about delivery. A message can be sent, delivered, and read, and those are three different states. A design that shows one checkmark for all three is lying to the user, and interviewers notice.

</TopicDefinition>

## How a strong candidate opens

"Assume a one-to-one and small-group chat product. For this interview, I will design the frontend: the message list, the send flow, the connection lifecycle, and presence. I will assume a websocket gateway, a history endpoint with cursor pagination, and server-assigned sequence numbers. I will not design the backend fan-out."

Then walk one message end to end before touching anything else. Type, send, optimistic render, ack, reconcile, receipt. That single journey contains almost the whole design.

## The optimistic row and its reconciliation

The mechanism that matters most is the pending row. It renders immediately with a local id, and the server ack swaps the local id for the real one. Everything else in the design protects that swap.

<CodeExample title="Optimistic send and reconcile" language="javascript">
{`function createChatStore() {
  let messages = [];
  let pending = new Map();

  function sendLocal(text) {
    const localId = 'local-' + Date.now() + '-' + Math.random();
    const row = { id: localId, text: text, status: 'sending' };
    messages = messages.concat([row]);
    pending.set(localId, row);
    return localId;
  }

  function reconcile(localId, serverMessage) {
    const row = pending.get(localId);
    if (!row) return;
    messages = messages.map(function (m) {
      return m.id === localId ? serverMessage : m;
    });
    pending.delete(localId);
  }

  function getMessages() { return messages; }
  return { sendLocal, reconcile, getMessages };
}

const store = createChatStore();
const localId = store.sendLocal('hello');
store.reconcile(localId, { id: 'msg-42', text: 'hello', status: 'sent' });
console.log(store.getMessages()[0].id, store.getMessages()[0].status);
`}
</CodeExample>

<Callout type="gotcha">
Never key the list by array index. When the optimistic row reconciles into the server row, or when history pages prepend, index keys make React reuse the wrong DOM nodes and the list glitches. Key by message id, and give pending rows stable local ids.
</Callout>

## Requirements

Functional requirements:

- Send and receive text messages in one-to-one and small-group conversations.
- Show sending, sent, delivered, and read states distinctly.
- Load history when scrolling up, without losing the current scroll position.
- Show typing indicators and online presence.
- Work across reconnects without losing or duplicating messages.

Non-functional requirements, stated as interview assumptions:

- Assume messages must feel instant: the optimistic render happens before any network round trip.
- Assume conversations can grow long, so the list must virtualize.
- Assume mobile networks drop often, so reconnect and resume are core flows, not edge cases.
- Assume message order is a correctness requirement, not a cosmetic one.

## API surface

Illustrative frontend contracts:

- `GET /conversations/:id/messages?before=<cursor>&limit=50` returns history pages, newest first, with a cursor for older pages.
- A websocket connection carries: client-to-server `send` events with a local id, and server-to-client `message`, `ack`, `receipt`, and `typing` events.
- Every server message carries an id and a strictly increasing sequence number per conversation. The client orders by sequence number, never by client timestamp.
- `POST /conversations/:id/read` marks up to a given sequence number as read, debounced on the client.

## Component tree

- `ChatScreen` owns the connection state, the message store, and the send box. It shows a connection banner when offline or catching up.
- `MessageList` is a virtualized list anchored to the bottom. It prepends history pages without moving the viewport, using measured heights and scroll anchoring.
- `MessageRow` renders one message with its delivery state. Pending rows show a sending indicator, failed rows show a retry action.
- `SendBox` owns the draft, the send action, and attachment affordances. It clears the draft only after the optimistic row renders, not after the ack.
- `PresenceBar` renders typing indicators and online state from ephemeral presence events, separate from the message store.

## Data flow

Sending appends an optimistic row and transmits the message with its local id. The server ack returns the real id and sequence number, and the store reconciles the row in place. Incoming messages merge by server id into sequence order. History loads on scroll-up: fetch the page before the oldest cursor, prepend it, and restore the scroll offset so the viewport does not move. On disconnect, the client shows a reconnecting state and backs off exponentially. On reconnect, it resumes from the last confirmed sequence number and merges the gap by id. Typing events throttle to one every few seconds with a stop event on pause, and expire on their own if the stop event is lost.

## Trade-offs

| Decision | Option A | Option B | Pick |
| --- | --- | --- | --- |
| Transport | Websockets | Polling or server-sent events | Websockets. Chat is bidirectional and frequent both ways. |
| Send feel | Wait for server, then render | Optimistic render, reconcile on ack | Optimistic. Waiting makes every message feel slow, and chat slowness kills the product. |
| Ordering | Client timestamps | Server sequence numbers | Server sequence numbers. Client clocks skew, and two clients can stamp the same millisecond. |
| History | Load all on open | Cursor pages on scroll-up | Cursor pages. Conversations are long, and loading all of one blocks the first paint. |
| List anchoring | Stick to bottom always | Smart stickiness | Smart stickiness: stay pinned only when the user is already at the bottom, otherwise hold position and show a "new messages" button. |
| Receipts | Per message receipts | Latest-only receipts | Latest-only, debounced. A receipt per message is a storm when the user scrolls fast. |
| Typing | Send on every keystroke | Throttle plus stop event | Throttle plus stop, with expiry. Keystroke events are chatty and pointless. |

## Failure and edge cases

- The send fails: the row stays with a retry button. Never delete a failed message silently, and never auto-retry forever without telling the user.
- The ack arrives after the user already saw the message echoed from another device: merge by server id collapses the duplicate, and the pending row reconciles to the same id.
- The connection drops mid-history-load: the history request aborts, the list keeps what it has, and scrolling up retries. No partial page is ever rendered as complete.
- Two devices send simultaneously: both messages get server sequence numbers, and both clients order by them, so both views converge to the same order.
- The gap on reconnect is huge: cap the catch-up page and show a "catching up" state, then let the user scroll up for the rest, rather than blocking the conversation on a giant replay.
- A message arrives while the user is scrolled up reading history: do not yank them to the bottom. Show a "new messages" button and jump only on tap.
- Clock skew between devices: irrelevant by design, because ordering never uses client time.

## If they push deeper

Name the next levels honestly. End-to-end encryption changes the message format and key management, and it is a large topic on its own. Media messages add upload, thumbnail, and transcoding flows, which the media gallery topic covers. Message search across conversations is a backend indexing problem with a frontend results page like the search topic. On the frontend, the next level is measurement: send-to-render latency, ack time, reconnect duration, and duplicate rate, each with a budget.

<Callout type="interview">
The classic trap is ordering by client timestamp. It looks obvious and it is wrong: two devices with skewed clocks produce messages that arrive out of order, and no amount of client sorting fixes a clock that lies. Interviewers ask about ordering precisely to hear "server sequence numbers." If you say timestamps, expect a follow-up about clock skew, and have no good answer ready unless you switch.
</Callout>
